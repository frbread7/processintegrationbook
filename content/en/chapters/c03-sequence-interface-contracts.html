Sequence order is an interface contract

Two modules may each be technically sound and still fail when placed in the same sequence. Which orderings and interface conditions must be true for the combined flow to remain compatible? The key is to describe modules by the state they require and the state they leave behind—not only by their names.

Learning objectives

  • Distinguish a strict process precedence from a preference or a conditional dependency.
  • Write interface contracts for material, geometry, surface, contamination, thermal history, and metrology.
  • Trace a sequence change to its downstream acceptance tests and evidence gaps.
  • Represent uncertainty without turning an untested concern into a claimed failure probability.

Describe each module by entry and exit state

For an integration review, a module is more useful as a state transformation than as a box labeled “etch” or “deposition.” Its interface contract should identify:

  • Entry state: incoming materials, stack and geometry, surface condition, pattern definition, and known prior history.
  • Operation boundary: what must be controlled or monitored, at what locations or structures, and which variables remain unknown.
  • Exit state: resulting geometry and material state, possible damage or residues, topography, and measurement evidence.
  • Compatibility conditions: downstream tolerances, thermal and chemical exposure limits, contamination controls, and any clean or queue constraints.

These are documentation categories, not universal numeric specifications. Real acceptance limits must come from validated process and product requirements. A contract that says “clean surface” is incomplete until the relevant surface property and verification method are defined.

Build a dependency graph with typed edges

Represent the candidate sequence as a directed graph, but label each relationship. A precedence edge means one operation must occur before another under the stated architecture. A compatibility edge means two modules must meet a shared condition. A budget edge records consumption of a cumulative resource such as thermal exposure or remaining thickness. A measurement edge specifies what evidence is needed before proceeding or deciding.

For each edge, record the condition, source, owner, evidence status, and consequence if violated. Separate established constraints from proposed hypotheses. Where order is flexible, record what makes it conditional rather than depicting one sequence as universally required.

Publicly reported: Mistry et al. report a platform that integrated high-k/metal gate transistors with a particular technology context. The paper supports studying material choice and process integration together; the DOI citation alone does not establish any specific sequence contract for another platform. Mistry et al. (2007).

Worked sequence review: an interface condition, not a recipe

Illustrative assumption: A proposed architecture places a sensitive material stack before a later operation whose thermal and chemical compatibility has not yet been established. The stack and operation are intentionally unspecified; this example provides no process parameters.

First state the uncertainty as a testable question: does the later operation leave the material/interface state within the downstream device and reliability requirements? Map the potential path: material properties before exposure → state after exposure → measurable device/interface response → acceptance decision. Mark every arrow as reported evidence, model result, or hypothesis.

Then compare options: retain the order and characterize the resulting interface; change the order if architecture permits; or select a different material/sequence candidate. For each, document new compatibility questions introduced by the change, including patterning, surface preparation, contact formation, and reliability. The evidence plan should include a control and a measurement sensitive to the suspected mechanism. If a simple model is used, document its valid range and calibrate it for the relevant materials before using it as a decision basis.

Yeo's review discusses metal-gate material selection and process-integration issues and can orient the reader to the coupled nature of such decisions. It is not evidence that a given stack will tolerate a particular undisclosed thermal or chemical exposure. Yeo (2004).

Typed contract example: verify the state after the operation that changes it

Synthetic interface case; no recipe or fab data. Suppose a downstream module requires a surface property to fall within a product-defined acceptance interval before it begins. An upstream treatment can change that property. The physical chain is treatment → changed surface chemistry or residue state → downstream nucleation/adhesion or electrical interface response → measurable acceptance evidence and manufacturing decision. Which surface metric and downstream observable matter must come from the actual module contract; no universal limit is implied here.

The valid order is treatment → measurement gate → downstream operation. If architecture requires a different order, the contract needs another measurement or a justified model that establishes the entry state. This is a logical evidence rule, not a claim that every treatment requires the same metrology step.

Limits of a sequence graph

A graph exposes logical dependencies; it does not calculate diffusion, reaction, contamination, defectivity, device shift, or yield. A missing edge is not proof of compatibility. Reviewers should look for unrecorded shared resources and ask whether each consequential edge has traceable evidence, an explicit owner, and a test. Detailed module mechanisms belong in the specialist references; the integration task is to connect their outputs to neighboring entry conditions.

Knowledge check

  1. A proposed sequence diagram places module A before B. What must be added for the diagram to support an engineering decision?
    Answer: State whether the ordering is mandatory or conditional, define the interface state B requires from A, identify the evidence and source for the constraint, and record downstream acceptance and residual risk.
  2. A graph contains no incompatibility edge between two modules. Can the team conclude they are compatible?
    Answer: No. Absence of a recorded constraint can mean the interface has not been evaluated. Compatibility needs evidence under the relevant materials, sequence, and operating conditions.
